# 2026-09-24 成本裁剪：crime 清單、GMGN leg、writeDrain 積壓、zero-mcap row

一次過的「減 subrequest／減浪費呼叫」批次，連同兩個 backlog 嘅跟進。三項決定 + 兩項
診斷，全部有 live 讀數支撐（worker `solana-meme-bot.cool1999k.workers.dev`）。

## 1. 關掉 crime 名單載入（`CRIME_WALLETS_ENABLED = "false"`）

**理由**：gate 低產出，但成本照付。live 讀數：

| 來源 | 讀數 |
|---|---|
| `/debug/crime-wallets` | `enabled true`（該 isolate 未運行掃描 → `size 0, loadedAt null`）|
| 同一頁 `persistedUpdatedAt` | 1790242241837 = **2026-09-24 ~09:30Z** → 有 isolate 真係上網抓過清單（6h TTL 內）|
| `/debug/tick` | `crime 0`、`fails.crime 0` |
| `crimeWalletsConfigured` | `true`（client 照建） |

即係：清單**係**有載入（`persistedUpdatedAt` 係網絡路徑先寫），每 candidate 做
`checkToken` → 預設 `CRIME_WALLETS_CHECK_HOLDERS=true` → 最多 `holderTopN 8` 個 holder 要兩個
Helius RPC（`getTokenLargestAccounts` + `getMultipleAccounts`）；同時 cold isolate 每次都要
hydrate ~216KB 清單（兩次 `worker_state` 讀）。**判 hit 幾乎永遠 0**，而且
`CRIME_WALLETS_BLOCK=false`（display-only）→ gate 唔會擋任何 push。

**改動**：`wrangler.toml` 加 `CRIME_WALLETS_ENABLED = "false"`。config guard 係
`(env.CRIME_WALLETS_ENABLED ?? "true") !== "false"`，所以 `"false"` = client 完全唔建：
唔拉清單、唔 hydrate、唔花 holder RPC、卡片冇 crime flag。scanner 早就有 fail-open 分支
（`crimeClient ? … : null` 回傳空 result），所以唔會 throw。

⚠️ **唔係完全中性：連帶關掉 new-wallet 自拉 gate。** `checkToken` 解出嘅 `holders` 係
wallet analysis 唯一嘅 holder 來源（`analyze({ holders: crime.holders })`），而
new-wallet gate（`WALLET_NEW_RATIO_MAX` / `WALLET_NEW_MIN_CHECKED`）嘅輸入就係
`wallet.holders.checked/newWallets`。crime client 唔建 → `holders: []` → `checked 0` →
該 gate 永遠唔會判（fail-open）。即係用「crime flag + new-wallet gate」換走每 candidate
嘅兩個 Helius RPC。

**要保留 new-wallet gate 就要解耦**（唔喺今次範圍）：令 holder resolution 獨立於 blocklist
（例如 crime client 即使 `loaded:false` 都照 resolve holders，只係唔判 hit），咁就可以關
清單載入而保住 gate。要嘅話另開一個 apply patch。

**恢復**：`/debug/crime-wallets` 證明清單載到，再考慮開返 `"true"`。

## 2. 停 GMGN leg（`GMGN_TRENDING_LIMIT = "0"`）

**理由**：GMGN edge 以 IP 級 429 封 Cloudflare Worker 嘅共用 egress，leg 永遠交唔到幣。
live `/health.gmgnFeed`：`requests 9 / http429 9 / consecutive429 9 / lastStatus 429`，
每次掃描 `gmgn 0`；`/debug/gmgn` 答 `ok true, count 0`。

**改動**：`GMGN_TRENDING_LIMIT = "0"`（`0` = leg off）。client 自己每次 429 後停 5 分鐘
（`GMGN_RATE_LIMIT_BACKOFF_MS`），所以唔係「每 tick 白撞」，但仍係每個 5 分鐘窗口一個
注定失敗嘅請求，加上共用同一 backoff 嘅 per-candidate `/token/info`。

**刻意保留 `GMGN_ENABLED`**：呢個 switch **唔**覆蓋 candidate enrichment（smart-money
count／wash-trading flag／`GMGN_BLOCK_WASH_TRADING` gate）。要一次過移除成個 client 就設
`GMGN_ENABLED = "0"`（AXIOM_ENABLED 式）；但咁樣 `/debug/gmgn` 就再冇 client 可探，失去
「證明封鎖已解除先恢復」嘅驗收路徑，所以今次只關 leg。恢復條件：`/debug/gmgn` 證明封鎖
走咗。

## 3. Gecko：維持現有 backoff（唔補 key）

gecko **已經**有分級 backoff：`GECKO_RATE_LIMIT_BACKOFF_MS` 5 分鐘，之後每連續 429 加倍
（5→10→20→40→60），上限 `GECKO_BACKOFF_MAX_MS` 1 小時／`GECKO_BACKOFF_HARD_MAX_MS` 6 小時，
加邊緣快取路徑（見 `docs/gecko-429.md`）。live `geo 0 / geoTrend 0` 但唔再係每輪硬撞。

`COINGECKO_API_KEY`（demo plan）**唔補**：demo 嘅 10K calls/月 遠低於本 bot 約 86K/月，
只會將 quota 由共用 IP 搬去 key 上，覆蓋唔到。要補嘅話：喺 Keys/Cloudflare 設
`COINGECKO_API_KEY`（secret）+ `COINGECKO_API_PLAN=demo`。冇 key 時 gecko client 照行免費
路徑 + alternate-host fallback。

## 4. writeDrain 積壓（47 pending / 38 failures）——令原因可見

`pending 47` + `totals {calls 57, failures 38}`（67% 失敗）係一個真 backlog，但
`/health.writeDrain` 只有 `pending`／`failures`，**從來冇講點解**──原因只去得到
`wrangler tail`（transport abort？Turso 5xx？寫入太大？conflict？）。drain 一撞第一個
失敗就停批，所以「邊條 entry 卡住」就係答案。

**改動**（`src/tickprobe.ts`，喺編輯窗內）：

- `WriteDrainView` 加 `lastError: { name, message, at } | null` —— 本次 drain 最新一條失敗
  entry 嘅 method／錯誤文字／時間，冇失敗就 `null`。
- `drainDeferredWrites` 喺 catch 記落嚟，寫入最終 view；空批 / 乾淨批保留 `null`。
- `resetTickProbe` 一併重設。

**驗收**：`scripts/test-tick-path.js` 加咗斷言──失敗批 `lastError.message === "turso 522"`、
`name === "Error"`、`at` 係數；下一次成功批 `lastError === null`。所以下一次見到
`pending` 高企，`/health.writeDrain.lastError` 就講到邊條寫入、咩錯。

## 5. `push_watch` 兩個 zero-mcap row —— 自我修復 fallback 落咗 0

`/debug/push-watch` 40 行之中，**兩行** `mcapAtPush 0`：

| token | symbol | pushedAt | mcapAtPush | peakMcap |
|---|---|---|---|---|
| `7RQBQ1wqfrsCrAPVdjEuMVTfJuoXAEDgz87XkuuX3y2A` | 💲 | 2026-09-24 ~03:35Z | **0** | 221150 |
| `BtpekseAAyyaxRsr48JAjoa8BTBozjFNkBY6E9nv2d2V` | 玉兔 | 2026-09-24 ~04:26Z | **0** | 70921 |

**成因**：`push_watch.mcap_at_push` 有三個寫入者（見 `src/pushledger.ts` 開頭）。呢兩行唔係
push 本身寫（gate 值一定 > 0），而係 tracker 自我修復（self-heal）補寫──幣喺 push 當時
冇入到 watch 表（isolate 喺 push 同 enroll 之間死咗），補寫時個 baseline 用
`known?.mcapAtPush ?? pair.marketCap`。`known`（push 基線帳簿）冇該 token，而 DexScreener
當刻對嗰個 pair 報 `marketCap 0` → baseline 落 0。

**後果**：`chgSincePush = (live.mcap / max(mcapAtPush,1) - 1) * 100` 爆錶、recap 顯示
「推送 $0」、dead-state 復活地板 `(deadTroughMcap ?? mcapAtPush) * 1.5` 塌到 0（任何正讀數
都會「復活」該行）。

**改動**（`docs/patches/pushwatch-zero-mcap-baseline.apply.js`，因為 `pushwatch.ts` 第 ~2290
行超出 file-tool 窗口）：

```
node docs/patches/pushwatch-zero-mcap-baseline.apply.js
```

優先取正嘅 `marketCap`，冇就取正嘅 `fdvUsd`（同 dexscreener leg 嘅 `mcapFromFdv` 替代一致），
兩者都冇就**跳過呢次 enroll**（冇估值嘅 pair 根本無從追蹤，下一個 pass 有讀數時再補）。
不會再寫出 0 baseline。

**測試 pin**：`scripts/test-tick-path.js` 檢查四個 marker 要麼全中、要麼全冇（
`pushwatch.ts` 第 ~2290 行超出窗口，所以 pin 放喺呢度而唔係 `test-unit.js`）。
