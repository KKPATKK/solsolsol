# Pool Pin：追蹤行只判自己開卡嗰個池（2026-10-02）

> 承接 `docs/mcap-basis-and-pool-pick-2026-10-02.md` §5.3：
> 「`fetchPairsForTokens` 只拿到『每個 token 一個 pair』，所以 tracker 冇得知道自己行開嗰個池
> 係咪仲喺 response 入面 —— 即係『行唔會跟住換池』呢件事未做。要再硬淨啲，就要喺 `push_watch`
> 加 `pool_address`（pin 池），換池嗰 pass 唔判斷；呢個係下一步。」
>
> 政策（2026-10-02 決定）：**偵測到換池嗰 pass 唔判 → 跟住 re-pin 新池 → 下一 pass 用新池續判。**

---

## 1. 問題（量度，唔係推斷）

Agency 事故（2026-10-02 20:11 HKT）同一個 mint、8 個池、mcap $48K–$3.3M：

| 池 | mcap | LP |
|---|---|---|
| pumpswap（主池） | 2.83M–3.57M | 198K–222K |
| meteora（薄池，價凍結） | 2,284,414 | 9,958 |
| meteora（壞比例） | **3,058** | 85,154 |
| pumpfun curve 殘留 | 48,561.93 | null |

一條行嘅 series（`mcapAtPush`、`peakMcap`、`deadTroughMcap`、`lastLiquidity`）全部屬於**一個池**，
但 tracker 讀「token batch 揀（最深池 wins）嘅池」——換池之後冇人知，靜默用第二個池嘅數
繼續判 → 💀 卡現價 0.50× 市場（見該文 §2）。`pool_address` 就係令行記得自己個池。

## 2. 設計

### 2.1 Pin 幾時寫

| 時機 | 寫乜 | 來源限制 |
|---|---|---|
| 開卡 `onPush` | `pool_address =` 卡上嗰個池 | 只認 DexScreener pair（`pinnablePoolAddress`） |
| self-heal `enroll` | 同上（heal 用嘅 pair） | 同上 |
| Legacy row（NULL）第一次成功 check | 佢實際被判嗰個池（write-once） | 同上 |
| 確認換池（`Db.repinPushWatchPools`） | 新池，CAS `WHERE pool_address = 舊值` | token batch 嘅代表池（DexScreener 來源） |

`pinnablePoolAddress`（`src/pushwatch.ts`）拒絕 Jupiter／Gecko：兩條腿嘅 `pairAddress` 係
**mint**（`jupfeeds.ts` `id`、scanner gecko snapshot），pin 佢＝行以後永遠搵唔到自己個池。
`feedSource` 缺席（fixtures／synthetic）＝ DexScreener，同 `liquidityIsComparable` 同一條規則。

### 2.2 Pass 點樣查池（by-address lookup）

`fetchPairsForTokens` 答唔到「你行嗰個池仲喺唔喺 response」，所以要另一個端點：

- `DexScreenerClient.fetchPairsByAddresses(addresses, deadline)`（`src/dexscreener.ts`）：
  `GET /latest/dex/pairs/solana/{addr1,addr2,…}`（一次 ≤30 個池、`pairs` 陣列），
  key = `pairAddress`，edge cache 120s（`PAIR_BATCH_CACHE_TTL_S`），同一條 throttle／429 block
  （`dexFeedLeg` 已將呢條 path 歸入 `pairs` lane）。
- `Scanner.poolPairsForTracker`（`src/scanner.ts`）：
  1. 先用今個 tick 前端已抓嘅 `lastPairs` 按 `pairAddress` 對（免費；只認 DexScreener 來源）；
  2. 其餘一次過打 by-address；
  3. **冇 Jupiter／Gecko fallback**——兩條腿答「token 而家邊個池」，答唔到「我個池仲喺唔喺」。

回傳 `{ pairs: Map<string, PairInfo | null>, snapshots }`：**值 = 池仲喺 response 入面**；
**`null` = 問過、唔喺入面（確認換池）**；**冇 key = 冇答案（429／窗口用盡）＝ 唔係證據**。
`snapshots` = 今 pass 有幾多個 pin 由 last-answered snapshot 判（2026-10-03 加，見 §8）。

### 2.3 判決規則（row loop）

Pinned row 只讀自己個池：

1. by-address 有答案 → 判（就用嗰個池嘅數）；
2. by-address 冇（未問／冇答）但 token batch 嘅代表池 **地址相同** → 判（同一池，證明咗）；
3. 否則（by-address 冇答案，或確認唔喺 response）→ **嗰 pass 唔判**：
   - **確認換池**（`null`）：`pin-skip +1`，loop 後一次 batch CAS re-pin 去 token batch
     而家代表嗰個池（`repin +1`）→ **下一 pass 用新池判（剛好跳一個 pass）**；
   - **唔確定**（429／窗口）：`pin-skip +1`，pin 唔郁（錯唔到，慢一個 tick 就會再問）。

冇 pin 嘅 legacy row：照舊 token batch 判；第一次成功 check 寫入 COALESCE pin。

### 2.4 開關／讀數

- note 新增：` pins a/b`（b = 今 pass 問嘅 pin 數；a = 有答案嘅數，包括確認唔喺入面）、
  `pin-skip N`、`repin N`、`pin-snap N`（2026-10-03 加：由 snapshot 判嘅數）。
- `/debug/push-watch` 每行多咗 `poolAddress`（new rows 應有值）。

## 4. 成本 / 遙測

- 每 tracker pass 多 **1 個** DexScreener request（有 pin 先打；≤30 池 batch 成一個），
  同 token batch 共用 pair stage（`spent.pairs` 計時已包括；各自有 `TRACKER_PAIRS_BUDGET_MS` 窗口）。
- Edge cache 120s：pin 地址組穩定 ⇒ 2 分鐘內嘅重覆 pass 有機會 hit，唔會吓吓打 origin。
- 429 讀數照計落 `pairs` lane（`dex.http429` / `batchBlockedUntil` / spacing）。

## 5. 驗收（上線後睇）

1. `/debug/push-watch`：新 push 嘅行 `poolAddress` = 卡上嗰個池（唔係 mint）。
2. note：正常 pass `pins N/N`（N＝有 pin 嘅 active rows）；之後有換池嗰一 pass 見到
   `pin-skip` ＋ `repin` 各 1，下一 pass 回復正常且 `lastMcap` 貼新池。
3. 429 風暴期間：pinned rows 寧願 skip（`pin-skip` 升、無 `repin`），唔會用陌生池出卡。

## 6. 已知限制（設計上接受，唔係 bug）

1. **Re-pin 唔會 reset series**（peak／trough／lastLiquidity 照舊）——一個 pass 嘅 grace
   就係全部保護（政策：跳一 pass 後用新池續判）。
2. Token 完全冇 pair（pin 同 token batch 都搵唔到）→ 嗰行每個 pass 都 skips、唔會被刪，
   等窗口 prune 收。
3. Legacy rows 要等第一次成功 check 先 pin；之前仍然係 token-batch 判（≤43h 全換代）。
4. Pin lookup 係 best-effort：DexScreener 429／窗口用盡 → 嗰 pass pinned rows 先食
   last-answered snapshot（≤90s，見 §8），冇 snapshot 先 skip（安全方向，慢一個 tick）。

## 7. Rollback

- Pin 係純附加：回滾 = deploy 上一版 code。DB 多咗 `pool_address` 欄（inert，舊 code 唔讀）
  → 冇 schema 回滾問題，亦冇 data migration。

## 8. 2026-10-03 補丁：短 TTL last-answered snapshot

上線後一個鐘觀察：429 期間 token lane 照有答案（`pairs 23/23`，食 edge cache），但 pin lane
多數要真請求 → 全員 skip（`pins 0/23 pin-skip 23`；抽樣只得 ~3/16 pass good）。補法：
by-address **冇答案**時，用同一池最後一次 answered 嘅 snapshot（TTL 90s）續判；snapshot 只係
判數用途，唯一 repin 觸發仍然係「answered 且缺席」。記憶係 per-isolate，另外有一個 colo
載體（`caches.default`）令冷 isolate 都用得着。詳見 `docs/pin-snapshot-2026-10-03.md`。
