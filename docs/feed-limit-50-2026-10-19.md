# 2026-10-19：三條 launch feed 嘅 20 → 50，同 wrangler.toml 對齊

## 0. 結論

| # | 讀數 | 處理 |
|---|---|---|
| 1 | live 由 **05:05:57Z** 起，pump.fun 同 Raydium LaunchLab 每 tick 嘅交付上限都由 **20 變 50**；repo `wrangler.toml` 一直寫 **20** | ✅ 三個 knob（`PUMPFUN_PROFILE_LIMIT`、`METEORA_FALLBACK_LIMIT`、`RAYDIUM_LAUNCH_LIMIT`）都係 **50**，連註釋／測試釘一齊更新（見 §2） |
| 2 | 成因係 **dashboard 改過 Worker vars**，唔係 code：兩個唔同 feed 喺同一秒一齊變 50，而 `wrangler deploy` 只會套用 toml 嘅值 | 呢個係本文件存在嘅原因：dashboard 係第二個 source of truth，下次 deploy 會靜靜哋把兩個 feed 減半 |
| 3 | 50 之下嘅 240-tick 窗口（同日較早時嘅 audit） | 240/240 ok、**120.0 tick/h**、gap p50 29.99s／max 45.14s、每條啟用 feed 喺每個 due tick 都有交付、冇漏推 —— 所以 50 留住 |

一句話：**唔係 code 飄移，係 env 飄移；repo 而家寫返生產實際跑嘅 50，下次 deploy 唔會再無聲減半。**

## 1. 量度

- 同一把尺：`/debug/scan-history?rows=240`（240/240 ok、0 error、gap p50 29.99s、
  max 45.14s、120.0 tick/h），加 `/debug/tick-legs` 嘅 240 行 per-leg 交付數。
- 05:05:57Z 之前：pump 同 raydium 每 tick 最多 20；之後：最多 50。兩個 feed 由
  同一秒開始變，所以係一次過改兩個 var，唔係其中一條 feed 自己壞。
- 覆蓋／推送冇變：追蹤池 17/17 每 pass 全檢（issueCount 0）、推送帳本 183/183
  authoritative（pending/duplicate 0）、240 tick 內冇 ≥60s 空窗。
- 慢 tick（有候選時跑到 chainDeadline 8.1s）同呢個改動無關：flow 分析量到 6.6s
  花喺 chain，唔係 feed；45s gap 係已知嘅 cron backstop 形狀。

## 2. 改動

- `wrangler.toml`
  - `PUMPFUN_PROFILE_LIMIT = "50"`（原 20）。pump.fun 每頁 20 行，所以 50 =
    **每 tick 3 個 request**（原本 1 個），約 **+240 subrequest/hour**，新幣註冊
    （D1 writes）最多 **2.5×**。
  - `METEORA_FALLBACK_LIMIT = "50"`（原 20，已喺 commit `d23f109` 落）。
    `page_size` 係同一個 request 嘅參數，所以只係多咗 parse，**零額外 subrequest**。
  - `RAYDIUM_LAUNCH_LIMIT = "50"`（原 20）。頁本身係 100 行，**request 數不變**
    （仍然每 tick 1 個），只係 slice 闊咗，所以係免費嘅覆蓋。
  - 兩個 block 嘅註釋寫明：50 係 2026-10-18 05:05:57Z 嘅生產值、240-tick audit
    支撐、以及要縮返 20 時**幾個 var 一齊改**（唔好留下 dashboard 做第二個真相）。
- `src/config.ts`、`src/pumpfun.ts`、`src/scanner.ts`、`src/worker.ts`、
  `src/raydiumlaunch.ts`：只改描述生產值嘅註釋（`= 20` → `= 50`、Raydium 嘅
  slice、pumpfun.ts 嗰句過時嘅「It is 0 in production」）。
- `scripts/test-unit.js`：`wrangler.toml` 嘅釘由 20 改 50
  （`PUMPFUN_PROFILE_LIMIT`、`METEORA_FALLBACK_LIMIT`、`RAYDIUM_LAUNCH_LIMIT`）。
  chain helper 嘅 `PUMPFUN_PROFILE_LIMIT: "20"` 係 **fixture** 值，唔係生產值：
  佢只係要餵一個 always-on limit，值幾多唔影響被測嘅 chain 形狀。config
  parse／clamp 嘅測試照舊（40、0、9000、junk 等）。

呢個 commit 同 `d23f109`（另一條 session 已推上 origin 嘅同一個改動）嘅分別：
數值一致，但呢邊多咗 §0 第 2 行嘅 dashboard 飄移記錄，以及 `src/config.ts`、
`src/pumpfun.ts`、`src/scanner.ts`、`src/worker.ts`、`src/raydiumlaunch.ts` 嘅
過時註釋。rebase 時 `wrangler.toml` 同 `test-unit.js` 嘅衝突以 origin 嘅版本為
底（數值一樣），只保留呢邊嘅漂移解釋。

## 4. 限制（照實講）

- **寫呢份文件時讀唔到 live 配置**：Worker 嘅 workers.dev host 對所有 path
  （`/health` 都係）回 `404 error code: 1042`，所以冇辦法喺改完之後再讀一次
  `/debug/tick` 確認 50。上文嘅 50 係同一次 audit 喺生產量到嘅實際交付上限。
- Cloudflare dashboard 嘅 vars 唔喺 git，亦冇 API token 喺呢個環境可以列出
  Worker 版本嘅 vars；所以「dashboard 改過」係由兩個 feed 同一秒一齊變推斷，
  唔係直接讀到 dashboard。
- 如果 50 其實係誤改，正確做法係喺 `wrangler.toml` 將兩個 var 改返 20 再
  deploy（一次過、有 commit），唔好淨係改 dashboard。
