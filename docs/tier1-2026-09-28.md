# Tier 1 (2026-09-28): take the re-eval pool off the tick's critical path

Three changes, all motivated by one reading: the tick's own clock was dominated
by **DB round trips that did not have to be in series**, not by CPU, not by
subrequests (26 of 1,000), and not by the tick budget (8,000ms of an ~2,300ms
tick).

| # | change | where |
|---|---|---|
| 1 | the re-eval pool read is **dispatched with the feed fan-out**, not after it | `src/scanner.ts` |
| 2 | the `token_stats` prune is dispatched beside it (independent DB call) | `src/scanner.ts` |
| 3 | the pool read goes through the **colo edge cache** (Cache API), keyed by rotation slot | `src/scanner.ts`, `src/db.ts` |

Commits: `26fe7b7` (1+2) → `a362d18` (3, plus the `poolMs` metric fix) →
`4ba5021` (the hit-path proof).

## What it measured

Per-tick wall clock from `/debug/scan-history` (the tick ring, 120 rows):

| window | n | avg | p50 | min | max |
|---|---|---|---|---|---|
| before 10:08Z (baseline) | 95 | 2,708ms | 2,558ms | 1,521ms | **4,757ms** |
| items 1+2 (10:08–10:18Z) | 10 | **2,322ms** | **2,259ms** | 2,079ms | 2,742ms |
| item 3 (10:18Z→) | 15 | 2,461ms | 2,343ms | 2,188ms | 3,358ms |

≈**−390ms avg / −215ms p50**, and the long tail is gone: the old max was a
4.76s tick (a slow DB window landing on top of a serial read).

The phase reading that says WHY — `summary.poolMs` (the read's own duration)
against the new `summary.poolWaitMs` (what the tick waited for it at the join):

```
poolMs 132–301ms   poolWaitMs 0 (every sample)   feedsMs 750–784ms
```

`poolWaitMs 0` on every tick is the whole result of items 1+2: the read is
finished by the time the feeds are, so the tick no longer pays it. On the ticks
where the in-memory query cache answers, `poolMs 0` (no read at all).

`poolMs` now times the **promise** rather than the clock at the join — as first
written it read `773` with `feedsMs 773`, i.e. the feed phase wearing the
pool's name (fixed in `a362d18`).

## Item 3's honest status: live, verified, and 0 hits so far

`summary.poolCache` after ~25 minutes of the new build:

```
{"available":true,"memory":7,"hits":0,"misses":7,"puts":7,"errors":0}
```

- **`available: true`** — the Worker runtime has the Cache API.
- **`puts 7, errors 0`** — every DB read seeded the slot's snapshot; the write
  path is proven live.
- **`hits 0`, and that is structural here, not a bug**: the cron ticks are
  served by ONE long-lived isolate (watch `memory` climb tick after tick), and
  its in-memory cache (TTL = the 90s rotation period) expires exactly when the
  slot advances. The isolate that needs slot *N+1* is therefore always the first
  to need it, so it must read the DB — no second isolate exists to hit its
  snapshot. The cache pays only when two isolates need the same slot: an
  isolate recycled mid-slot, a deploy, or a colo running more than one.
- The hit path is verified anyway, in `scripts/test-unit.js`, against an
  injected Cache API: put → match → JSON → a deep-equal against a row with
  every `TokenStats` field populated, the next slot NOT reading this slot's
  entry, and both malformed-entry shapes falling through to the DB read instead
  of becoming an empty pool.

If `hits` is still 0 after a week of deploys, the honest conclusion is that this
deployment is single-isolate and the cache can be dropped without changing
anything — the counters exist so that is a measurement, not a guess.

## What was deliberately NOT changed

- The per-phase upstream caps (`FEED_DEADLINE_MS`, `POOL_FETCH_BUDGET_MS`,
  `PAIRS_FETCH_BUDGET_MS`) — headroom, not limits (previous round).
- The absolute subrequest reserves — they simply stopped binding.
- Every bound in the pool query. Items 1–3 change **when** the read happens and
  **who** pays for it, never what it asks for: same SQL, same rows, same slice.

## Fallbacks (nothing new can take the tick down)

- A runtime without the Cache API (the Node container entry) returns null from
  `poolEdgeCache()` and behaves exactly as before the cache existed.
- A cache call that throws is counted (`errors`) and logged; the DB read
  answers instead.
- A cached row cannot double-push: the push path re-checks `isTokenSeen` (the
  dedupe the tick already reports as `candidates 1 / pushed 0`), and every gate
  is re-evaluated from live pair data.
- The key carries the rotation slot, and the dispatch pins the query's clock
  (`now: poolNow`) so the key's slot and the query's slot cannot disagree.
