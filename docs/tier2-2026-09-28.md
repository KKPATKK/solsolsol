Both discovery lists answer more rows than the tick kept, so the question was
whether the caps or the upstream were deciding coverage. The answer differs per
feed, and only a measurement separates them.

| # | dial | before → after | measured result |
|---|---|---|---|
| 6 | `JUPITER_RECENT_LIMIT` (config default) | 20 → **30** | ✅ `jup 30` per tick (was 20) |
| 7 | `DEXSCREENER_BOOSTS_LIMIT` (wrangler) | 20 → **30** | ❌ `boosts 17` — no change |

Commit `e15f570`, version `261abe89-ef13-4112-935a-1c674b477ff2`.

## Item 6 — worked, because the rows were already in the response

`JupTokensClient.fetchRecentTokens` asks for `/recent?limit=N` and then slices
the parsed rows to `N` client-side, because the endpoint answers ≥30 rows
whatever the parameter says (measured 2026-08-21). So the cap was deciding how
many of the rows **already in hand** got used, not how many the upstream was
asked for:

```
before: jup 20   after: jup 30     (one subrequest either way, same host)
```

+10 seconds-old launchpad launches per tick — the freshest coins the scanner
sees, and the lane the blocked pump.fun frontend feed used to fill.

## Item 7 — a measured no-op, recorded as one

`/token-boosts/latest/v1` answers 30 rows, and 30 is the config's clamp, so the
dial was raised to it. The leg still reads:

```
before: boosts 17   after: boosts 17
```

The reason is in the client: the loop **filters `chainId !== "solana"` first**
and slices afterwards. The upstream's 30 rows are cross-chain, so the Solana
subset — the only rows this feed can return — was already under the old cap of
20. Raising the dial costs the same single request, so it stays at the ceiling,
but the config comment now says plainly that the binding constraint is how many
Solana boosts exist, not how many rows are asked for. Recorded so the next
reader does not re-run the experiment.

Neither dial adds a request, a host or a rate-limit bucket: the tick already
fetched both lists. The only growth is ~10 coins walking the pair + gate path
(item 7 added none), which the tick's own window absorbs — p50 is flat and the
only long tick in the window is the one that delivered a card (`pushed 1`,
evalMs 4,290ms, the enrich path, not the feeds).

## The counters that decide whether item 6 stays

- `summary.jup` — must read 30, not 20 (a silent revert is what the new unit
  test pins).
- `dex.http429` / `budgetDrops` — the feed is one request; these must stay flat.
- `tokenStatsCount` and the pool band scans — every net-new coin grows
  `token_stats`, which is the cost side. If the pool's rows-read ever outweighs
  the launches this lane finds, `JUPITER_RECENT_LIMIT` is the first dial to
  lower (it is the only one whose value decides how many rows are used).
