# 大槓桿落地：DO + alarm 破 1 分鐘 cron cadence

> 2026-10-02。Cron Trigger 係 5 欄表達式，最快 1 分鐘（`[triggers].crons`），所以
> 「掃描快過 1 分鐘」一直係平台下限，唔係代碼下限。呢次用 **Durable Object alarm**
> 做 sub-minute trigger（`src/worker.ts` `TickClock` + `wrangler.toml`
> `[[durable_objects.bindings]]`），但仍然**只做 trigger**：每個 tick 經既有 relay
> 落 placed fetch path（NRT，貼住 Turso），即 2026-10-02 relay v2 鋪好嗰條路。

---

## 1. 架構（一圖講完）

```
                     ┌───────────────────────────────┐
cron `* * * * *` ───► │  cron invocation（ORD）        │
                     │  relay scan → placed（NRT）    │──► placed fetch handler
                     │  armTickClock()（1 DO req/min）│──┐   = 真正 scan
                     └───────────────────────────────┘  │
                                                        ▼
                                       ┌────────────────────────────┐
                                       │ DO "tick-clock"（單一實例） │
                                       │ alarm() 每 CLOCK_TICK_SECONDS│
                                       │  ├ relay scan   (source=clock)
                                       │  ├ relay tracker(source=clock)
                                       │  └ 自己 re-arm（finally）    │
                                       └────────────────────────────┘
                                                        │
                                       同一條 relay → placed（NRT）
```

要點：

| 項 | 決定 | 原因 |
|---|---|---|
| DO 做咩 | **淨係 trigger**（2 個 relay POST + re-arm），唔讀 DB、唔寫 row | DO 位置係建立時嘅 hint，唔保證 NRT；relay 已經證明「work 喺 placed path 跑」係量到 single-digit ms 嘅形狀 |
| 兩個 delivery 併行 | `Promise.all([scan, tracker])` | 佢哋係兩個獨立 invocation；平台本來就同一分鐘送 scan＋tracker cron，併行唔係新事。串行會令 alarm span = 兩份 wall clock |
| 每 tick 跑 tracker？ | 係（同 scan 一樣每個 clock tick） | 💀/🚀 跟進嘅 cadence 都係同一條 lever |
| maintenance | 唔郁，繼續 `*/5` cron | 兩個 leg 係 interval-gated side effect，唔關 cadence 事 |

## 2. 閘門仍然係 cadence：時序算術

Clock **唔會**強行 scan；佢同 cron 一樣只係「問」。`scheduled` 用
`scanGateMs(clockMs)`（clock 開嘅時候 clock period 就係 cadence）：

| clock period | gate（＝ interval − min(30s, interval/2)，地板 5s） | 健康 tick 讀到嘅 age（＝ period − scan 3–4s） | 過唔過 |
|---|---|---|---|
| 15s | 7.5s | ~11s | ✅（餘 ~3.5s） |
| 20s | 10s | ~16s | ✅（餘 ~6s） |
| 30s | 15s | ~26s | ✅（餘 ~11s） |
| 60s | 30s（舊行為） | ~56s | ✅ |
| 90s | 70s（舊行為） | ~86s | ✅ |

所以：**late alarm、同秒嘅 cron arrival、仍未完嘅 scan** 全部照舊由 gate／
`claimScanLock` 仲裁，重疊機會同以前一樣係零。Clock 死 → cron 60s cadence 照跑；
cron 死 → clock 照跑；兩個都死 → HTTP rescue（120s）照舊。

## 3. 唔准污染 cron 嘅讀數（呢個係 uptime monitor 嘅命）

Clock arrival 係經 relay replay 入 `scheduled`，但**唔算 cron arrival**：

| cron 讀數 | clock tick 會唔會郁 | 後果 |
|---|---|---|
| `scheduled_tick_ring` / `scheduled_tick_total` | ❌（`cronTick = null`） | 死 cron 唔會因為 clock 仲跑而睇落「活着」 |
| pre-init arrival stamp / `scheduledTickFinishedAt` | ❌ | 同上；亦唔會製造假嘅「cron arrival 但冇 return」 |
| `scheduledTicks`（module counter） | ❌ | `/health.scheduledTicks` 繼續係 cron 專屬 |
| skip reason | ✅ **自己一個** `clock-gate` | 「cron 過密」同「clock 過密」可以分開睇 |
| scan trigger counter | ✅ **自己一行** `scan_trigger_clock` | `/health.scanTriggers.clock` = clock 真正驅動嘅份額 |
| heartbeat `via` / `relay` | `"clock"` / `"inner"` | 一眼睇出邊個 trigger、喺邊度跑 |

## 4. 開關同 rollback

- 開關＝ `wrangler.toml [vars] CLOCK_TICK_SECONDS`（**set = on**）。
- 關：dashboard 改 `"0"`（或刪 key）→ 下一個 alarm（≤30s）見到 `tickMs = 0` 就
  **唔再 re-arm**，cron 60s cadence 立即接管；唔使 code deploy。
- 數值 clamp `[15, 300]`：`"1"` → 15s（唔會 hot-loop），`"9999"` → 300s。
- `SCAN_INTERVAL_SECONDS` 保持 60（clock-off 時嘅 cadence）。clock 開嘅時候佢被
  clock period 蓋過，係刻意嘅：**一個數管一條 cadence**。

## 5. 成本（30s 設定）

| 項 | 數量/月 | 備註 |
|---|---|---|
| DO alarm | ~87.6K | 每個 alarm = 1 DO request |
| relay subrequests | ~175K | 每 alarm 2 個（scan + tracker） |
| placed Worker requests | ~87.6K scan＋~87.6K tracker | 同 cron 一樣嘅 invocation，只係密咗 |
| cron arm DO request | ~43.2K | **cron 做 keeper**：每個 cron scan delivery `POST /arm`；`/arm` 見到已有 pending alarm 就唔郁（唔會重置 phase） |

＝ 大約「plan included requests 嘅十分一」量級。真正要盯嘅係上游同 Turso：
**cadence ×2 = 上游 calls／Turso rows ×2**，而 429 係呢個 Worker 已知天花板。

## 6. Deploy 後驗收（照順序讀）

1. `GET /debug/clock` →
   `{ ok:true, on:true, tickMs:30000, alarmAt:<now+~30s>, ticks:N,
     lastResults:{scan:"relayed",tracker:"relayed"}, relayConfigured:true }`。
   `?arm=1` 可以手動 arm（唔會搬 pending alarm）。
2. `/health` heartbeat：`via:"clock"`、`relay:"inner"`、`colo:"NRT"`。
   ⚠️ 呢兩個欄係「DO fetch 自己 URL 都入 placed path」嘅唯一證據；如果 `colo`
   唔係 NRT 或 `relay` 唔係 `inner`，即係 DO 嘅 fetch 冇行 placement，要即刻回報。
3. `scanTriggers.clock` 上升（cron/http 比例自然下降）。
4. `/debug/scan-history` 間隔 < 60s（預期 ~30–34s：period + 每個 tick 自己嘅
   work ~3–4s）。
5. `/health.pushWatchPass` 時間戳間隔 ~30s，`db` 仍然係單/雙位數 ms。
6. `/debug/dex429` `lastHour`、`summary.geoDue`、`summary.429` 冇惡化；
   `fails.organic` 等閘門數字正常。

## 7. 已知限制（誠實項）

- **Alarm 係 best-effort**：可以遲，唔會早。實際 cadence = period + 該 tick 嘅
  work（re-arm 喺 work 完成後）。所以 30s 設定實測應該係 ~32–36s，唔係 30.0s。
- **重啟／deploy**：新 version 會重置 DO instance（in-memory `ticks` 歸零），
  但 alarm 係 durable，`alarmAt` 唔會失；就算失，下一個 cron scan 會 arm 返。
- **Tracker pass row 嘅 `via` 仍然係 `"cron-pass"`**：clock 同 cron 嘅 pass
  用同一條路入 `runTrackerInvocation`，分辨要靠時間戳間隔（scan 側已有
  `via:"clock"` + counter，pass 側冇加）。
- **未做**：`SCAN_LOCK_TTL_MS = 30s` 未跟 clock period 縮短；如果將來設 15s，
  一個死咗嘅 holder 會佔約兩個 tick（~30s），係可接受但要知道。
- **未做**：`maybeRunScanIfStale` 嘅 rescue gap 仍然用 `SCAN_INTERVAL_SECONDS`
  （120s 下限）——clock 死 + cron 死嘅情形下，rescue 仍然係 120s 後介入。
